# AgentRail은 표준 이름을 입고 원장에서 강제한다

**결론 먼저.** 2025~2026년 에이전트 결제 표준은 세 층으로 정리됐다. **신원 층**(RFC 9421 서명 기반 Web Bot Auth, Visa TAP, Mastercard Agent Pay, Skyfire KYA), **권한 위임 층**(AP2 mandate, ACP `allowance.max_amount`, x402 `upto`), **정산 층**(x402 v2와 XRPL `exact` scheme, T54 facilitator)이다. 어느 표준도 "에이전트 지출 한도를 원장이 강제하는 방법"은 정의하지 않았다. AgentRail의 "LLM 제안 → 코드 검증 → 원장 강제"가 들어갈 자리가 바로 여기다. 남은 약 5시간(03:10~08:00, PLAN 블록 3~6이 이미 이 시간을 채우고 있음)에 추가할 것은 네 가지로 한정한다. 시간은 PLAN이 "가장 먼저 줄인다"고 정한 dashboard polish에서 가져온다.

1. **x402 rail을 XRPL `exact` 스펙에 맞게 고치고 Testnet에서 1회 실행한다.** 스펙상 `Memos`는 금지이고 `InvoiceID`는 `sha256(invoiceId)`다. 지금 `engine._pay`의 memo 방식을 x402 경로에 그대로 쓰면 facilitator가 거부할 가능성이 높다. x402 보너스와 직결된다. 약 60분.
2. **기존 `mandates`·quote·order를 AP2 IntentMandate/CartMandate/PaymentMandate 이름과 해시 체인으로 다시 표현한다.** AP2 IntentMandate에는 금액 상한이 없으므로 `max_amount`를 우리가 추가하고, mandate 해시를 memo(Payment rail)와 `InvoiceID` 입력(x402 rail)에 넣는다. 심사위원이 아는 어휘로 "안전한 자율성"을 설명할 수 있게 된다. 약 45분.
3. **PLAN 블록 3(KYB: `VERIFIED_ORG` Credential + `DepositPreauth` `AuthorizeCredentials`)은 그대로 진행하되 x402 경로와 섞지 않는다.** 원장이 "미검증 기관의 돈은 받지 않는다"를 강제하는 것이 이번 해커톤 우승 패턴(가드레일)에 가장 가깝다.
4. **A2A Agent Card를 정적 JSON으로 노출하고 기관↔개인 에이전트 메시지를 A2A v1.0 모양(`SendMessage`, `TASK_STATE_INPUT_REQUIRED`)으로 로그에 남긴다.** SDK 통합은 하지 않는다. 약 30~40분.

Batch, Token Escrow(RLUSD/MPT), Permissioned Domain, x402 `upto`, Web Bot Auth 서명, Skyfire 연동은 이번에는 **넣지 않는다**. 대신 README의 "표준 정렬" 표에 한 줄씩 적는다.

## 표준 지형: 이름은 많아도 구조는 셋이다

**x402가 정산 층의 공용어가 됐다.** v2 스펙(2025-12-09)에서 서버는 `402`와 함께 `PAYMENT-REQUIRED` 헤더(base64 JSON, `accepts[]`)를 보낸다. 클라이언트는 `PAYMENT-SIGNATURE`로 재요청하고, 서버는 facilitator의 `/verify`·`/settle`을 거쳐 `PAYMENT-RESPONSE`를 돌려준다. v1의 `maxAmountRequired`는 `amount`로, 네트워크 표기는 CAIP-2로 바뀌었다 ([x402 v2 spec](https://raw.githubusercontent.com/coinbase/x402/main/specs/x402-specification-v2.md), [HTTP transport v2](https://raw.githubusercontent.com/coinbase/x402/main/specs/transports-v2/http.md)). 저장소는 `x402-foundation/x402`로 옮겨졌고, Linux Foundation 산하 x402 Foundation이 2026년 4월 출범했다. Ripple은 2026-07-14 Premier Member로 합류했다고 보도됐다 ([Linux Foundation](https://www.linuxfoundation.org/press/linux-foundation-is-launching-the-x402-foundation-and-welcoming-the-contribution-of-the-x402-protocol?hs_amp=true), [Börse Express](https://www.boerse-express.com/news/articles/xrp-ripple-tritt-x402-foundation-bei-928251)). 창립 회원 명단은 2차 보도라 확인이 필요하다.

**XRPL은 공식 스펙에 들어간 1급 네트워크다.** 네트워크 id는 `xrpl:0`(mainnet), `xrpl:1`(testnet), `xrpl:2`(devnet)다. payload는 `payload.signedTxBlob` 하나뿐이다. 우리 설계에 직접 영향을 주는 제약은 다음과 같다 ([scheme_exact_xrpl.md](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact_xrpl.md)).

- **`Memos`는 금지다.** 스펙은 "invoice binding must not use memos"라고 쓴다. `Delegate`, `Paths`, `DeliverMin`, XRP 결제의 `SendMax`, `tfPartialPayment`도 금지다.
- **`InvoiceID`는 `SHA-256(invoiceId)`**(64 hex)다.
- **`extra.areFeesSponsored`는 `false`여야 한다.**
- **facilitator는 blob의 `Sequence`가 현재 계정 sequence와 같은지 검사한다.**

마지막 항목 때문에 `XrplLedger._next_sequence`로 미래 sequence를 미리 서명해 50명에게 병렬로 보내는 `scenario.scene_d` 방식은 x402 경로에서 통과하지 못한다. 병렬이 필요하면 `ticketSequence`를 써야 한다. 정산 시 facilitator는 tx hash 기준 중복 방지를 하고 validated `tesSUCCESS`에서만 성공을 반환한다. 우리 엔진의 "서명 blob을 먼저 저장 → 같은 blob 재제출" 설계와 잘 맞는다.

**T54가 XRPL facilitator를 운영한다.** 2026년 2월 무렵 XRP·RLUSD를 지원하며 출시됐다 ([t54.ai on X](https://x.com/t54ai/status/2024484156487377388)). xrpl.org 안내에 따르면 testnet facilitator는 T54가 best-effort로 운영하며 SLA가 없다 ([xrpl.org agentic payments x402](https://xrpl.org/docs/agents/agentic-payments-x402), *snippet만 확인*). testnet 엔드포인트 `xrpl-facilitator-testnet.t54.ai`의 출처는 제3자 GitHub issue 하나뿐이다 ([issue #28](https://github.com/Reallyeasy1/Kevin/issues/28), *미검증*). 문서 snippet에 나온 hosted 주소는 `xrpl-x402.t54.ai`다 ([docs.t54.ai](https://docs.t54.ai/docs/xrpl/x402-facilitator), *snippet*). Python 패키지로는 `x402-xrpl`(0.4.0b1)이 있다 ([PyPI](https://pypi.org/project/x402-xrpl/0.4.0b1/)). XRPL `upto` scheme(payment channel 기반)은 PR #3023으로 **2026-10-22에 병합됐다** ([PR #3023](https://github.com/x402-foundation/x402/pull/3023)). 병합 3일 만에 T54 testnet이 이를 지원할 가능성은 낮다고 본다.

**권한 위임 층은 AP2가 어휘를 정했지만 금액 상한은 비어 있다.** AP2의 세 객체는 다음과 같다 ([AP2 mandate.py](https://raw.githubusercontent.com/google-agentic-commerce/AP2/main/code/sdk/python/ap2/models/mandate.py)).

| 객체 | 서명 주체 | 주요 필드 |
|---|---|---|
| IntentMandate | 사용자 | `natural_language_description`, `merchants`, `skus`, `intent_expiry`, `user_cart_confirmation_required` |
| CartMandate | 판매자 | `merchant_authorization` JWT 안에 `cart_hash` |
| PaymentMandate | 사용자 | `user_authorization` SD-JWT-VC가 cart·payment 해시에 서명 |

**IntentMandate 공식 모델에는 금액 상한 필드가 없다.** 제3자 가이드에 나오는 `max_amount`는 공식 스키마가 아니다 ([Medium 가이드](https://medium.com/@visrow/google-agent-payments-protocol-ap2-technical-guide-implementation-73ee772fe349)). 반면 OpenAI·Stripe ACP의 delegated payment는 `allowance{reason: one_time, max_amount, currency, merchant_id, expires_at}`로 상한을 명시한다 ([ACP rfc.delegate_payment](https://raw.githubusercontent.com/agentic-commerce-protocol/agentic-commerce-protocol/main/rfcs/rfc.delegate_payment.md)). 따라서 우리는 "AP2 구조 + ACP식 `max_amount`"를 쓰면서 그 사실을 문서에 밝히는 것이 정직하다. Google은 2026년 4월 AP2를 FIDO Alliance에 기증했다고 보도됐다 ([FIDO Alliance](https://fidoalliance.org/google-donates-agent-payments-protocol-to-fido-alliance/)). AP2 저장소에는 아직 태그된 릴리스가 없다.

**신원 층은 RFC 9421로 수렴했다.** Visa TAP은 RFC 9421 HTTP Message Signatures를 쓰며 서명이 merchant 도메인과 operation(browse/pay)에 묶이고 1회용이다 ([visa/trusted-agent-protocol](https://raw.githubusercontent.com/visa/trusted-agent-protocol/main/README.md)). 헤더 이름(`Signature-Agent`, `Signature-Input`)과 태그(`agent-browser-auth`/`agent-payer-auth`)는 2차 자료에서만 나온다 ([eco.com](https://eco.com/support/en/articles/14845482-visa-trusted-agent-protocol-tap-explained)). Mastercard Agent Pay도 등록된 에이전트의 요청 서명과 에이전트용 network token을 쓴다 ([Cloudflare blog](https://blog.cloudflare.com/secure-agentic-commerce/), *snippet*). Web Bot Auth는 IETF WG 초안 `draft-ietf-webbotauth-httpsig-protocol-00`(2026-09)이 됐다 ([IETF](https://datatracker.ietf.org/doc/html/draft-ietf-webbotauth-httpsig-protocol-00)). Skyfire KYAPay는 `typ: kya|pay|kya-pay` JWT를 `kyapay-token` 헤더로 보내며, `hid`(사람)·`apd`(플랫폼)·`aid`(에이전트) 클레임을 담는다 ([Skyfire docs](https://docs.skyfire.xyz/docs/verify-and-extract-data-from-tokens)). Stripe·Paradigm의 Tempo와 MPP는 2026-03-18 메인넷에 올라갔다 ([The Block](https://www.theblock.co/post/394131/tempo-mainnet-goes-live-with-machine-payments-protocol-for-agents)).

**에이전트 간 통신은 A2A v1.0과 MCP 2026-07-28로 갈라졌다.**

- **A2A v1.0**(2026년 3~4월)
  - 메서드 이름이 PascalCase로 바뀌었다: `SendMessage`, `GetTask`, `CancelTask`, `SubscribeToTask` 등.
  - Agent Card(`/.well-known/agent-card.json`)는 `supportedInterfaces[]`와 JWS `signatures[]`를 갖는다.
  - 클라이언트는 `A2A-Version: 1.0` 헤더를 보내야 한다. 비워 두면 0.3으로 해석된다.
  - `TASK_STATE_INPUT_REQUIRED`·`TASK_STATE_AUTH_REQUIRED`는 "사람이 승인해야 함" 상태에 그대로 대응한다.
  - Python `a2a-sdk` 최신은 1.2.3이다.
  - 출처: [A2A spec](https://raw.githubusercontent.com/a2aproject/A2A/main/docs/specification.md), [PyPI a2a-sdk](https://pypi.org/project/a2a-sdk/)
- **MCP 최신 스펙 2026-07-28**은 stateless 개정이다. `initialize`와 `Mcp-Session-Id`가 사라졌고, elicitation은 Multi Round-Trip Requests(`resultType: "input_required"`)로 바뀌었다 ([MCP blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/)). 호스트들이 아직 전환 중일 수 있어 데모 클라이언트에서 직접 시험해야 한다.
- Ripple의 XRPL AI Starter Kit(2026-06-10)에는 XRPL Docs MCP 서버와 x402 통합이 포함됐다 ([Cryptonomist](https://en.cryptonomist.ch/2026/06/11/ripple-xrpl-ai-starter-kit-2/)).

## XRPL 최신 amendment: Mainnet에 켜진 것만 쓴다

**기관 권한 스택은 Mainnet에서 켜져 있다.** 2차 트래커 기준 활성화 날짜는 다음과 같다 ([jakeclaver index](https://www.jakeclaver.com/xrp-ledger-amendments-complete-index/), [RippleX on X](https://x.com/RippleXDev/status/2019165474752524686)).

| Amendment | Mainnet 활성화 |
|---|---|
| Credentials | 2025-09-04 |
| MPTokensV1 | 2025-10-01 |
| PermissionedDomains | 2026-02-04 |
| TokenEscrow | 2026-02-12 |
| PermissionedDEX | 2026-02-18 |

Testnet은 Mainnet을 "가깝게" 따라간다고만 되어 있다 ([parallel-networks](https://raw.githubusercontent.com/XRPLF/xrpl-dev-portal/master/docs/concepts/networks-and-servers/parallel-networks.md)). 따라서 반드시 `feature` RPC로 확인해야 한다.

**Batch는 위험하다.** 원래 Batch는 서명 검증 결함으로 rippled 3.1.1에서 비활성화됐다 ([xrpl.org vuln report](https://xrpl.org/blog/2026/vulnerabilitydisclosurereport-bug-feb2026)). BatchV1_1과 fixBatchV1_2가 2026-10-09 Mainnet에서 활성화됐다는 보도는 2차 자료뿐이다 ([Finwire](https://finwire.io/news/crypto-news/xrp-ledger-batch-goes-live-enabling-bundled-transactions)). xrpl-py는 **5.1.0부터** BatchV1_1 서명을 지원하고 옛 형식을 버렸다 ([xrpl-py CHANGELOG](https://raw.githubusercontent.com/XRPLF/xrpl-py/main/CHANGELOG.md)). 문제는 **xrpl-py 5.0의 `Wallet.from_seed` 알고리즘 추론 변경**이다. 지금 업그레이드하면 `wallets.local.json`의 시드에서 다른 주소가 나올 수 있다. 코드 프리즈 5시간 전에 SDK 메이저 버전을 올리는 것은 하지 말아야 한다.

**MPT와 Token Escrow에는 숨은 함정이 있다.**

- MPT에 `DomainID`를 넣으려면 `tfMPTRequireAuth`가 필요하다. 그리고 PermissionedDomains와 **SingleAssetVault**가 모두 켜져 있지 않으면 `temDISABLED`가 난다 ([mptokenissuancecreate.md](https://raw.githubusercontent.com/XRPLF/xrpl-dev-portal/master/docs/references/protocol/transactions/types/mptokenissuancecreate.md)). SingleAssetVault는 아직 투표 중이다. 따라서 "MPT 라이선스를 Permissioned Domain에 묶는다"는 Testnet에서 막힐 공산이 크다.
- MPT는 DEX에서 거래할 수 없다. MPTokensV2가 `Supported::No`이기 때문이다 ([features.macro](https://raw.githubusercontent.com/XRPLF/rippled/develop/include/xrpl/protocol/detail/features.macro)).
- Token Escrow의 조건 ([escrowcreate.md](https://raw.githubusercontent.com/XRPLF/xrpl-dev-portal/master/docs/references/protocol/transactions/types/escrowcreate.md)):
  - IOU는 발행자의 Allow Trust Line Locking 플래그가 필요하다.
  - MPT는 CanEscrow와 CanTransfer가 모두 필요하다.
  - 수신자가 미리 MPT를 보유하거나 trust line을 갖고 있어야 한다.
- Testnet RLUSD 발행자 `rQhWct2fv4Vc4KRjRgMrxa8xPN9Zx9iLKV`가 locking 플래그를 켰는지는 확인되지 않았다. 테스트 RLUSD 수령은 tryrlusd.com에서 하루 10개, API 없음으로 보고됐다 ([docs.ripple.com](https://docs.ripple.com/products/stablecoin/developer-resources/rlusd-on-the-xrpl), [dassie PR #244](https://github.com/justmoon/dassie/pull/244)).

**PLAN 블록 2(Escrow 키 공개)는 XRP escrow라 영향이 없다.** 다만 세 가지를 확인해야 한다.

- K는 `EscrowFinish`의 fulfillment로 **원장에 공개된다.** 번들은 K와 구매자의 box 키로 이중 봉인해야 한다. 그래야 sealed blob을 손에 넣은 제3자가 K만으로 열 수 없다.
- seller에 DepositAuth를 켜면 제3자의 `EscrowFinish`는 막힌다. 반면 destination(seller) 본인이 finish하는 것은 허용된다 ([depositauth.md](https://raw.githubusercontent.com/XRPLF/xrpl-dev-portal/master/docs/concepts/accounts/depositauth.md)). 따라서 블록 2와 블록 3은 "seller가 직접 finish"로 맞춰야 한다.
- 다른 계정이 credential로 통과해야 하는 경우에는 `Payment`·`EscrowFinish`에 `CredentialIDs`를 넣어야 한다 ([escrowfinish.md](https://raw.githubusercontent.com/XRPLF/xrpl-dev-portal/master/docs/references/protocol/transactions/types/escrowfinish.md)).

## 해커톤 우승작과 데이터 사례가 가리키는 방향

**우승작은 "재사용 가능한 인프라"와 "에이전트 가드레일"에 몰렸다.** Cronos x402 PayTech에서는 1위가 AgentFabric(execution fabric), 2위가 Cronos Shield(에이전트 보안)였다 ([DoraHacks winners](https://dorahacks.io/hackathon/cronos-x402/winner)). Coinbase Agents in Action에서는 MCPay.fun 같은 MCP paywall이 x402 부문을 받았고 ([Coinbase](https://www.coinbase.com/developer-platform/discover/launches/agents-in-action-winners)), EF x402 해커톤에서는 payment channel 프로젝트가 수상했다고 보도됐다 ([Phemex](https://phemex.com/news/article/ethereum-foundation-concludes-x402-hackathon-announces-winning-projects-54134), *aggregator*). **찾은 모든 우승작 목록에 건강·동의 데이터 프로젝트는 없었다.** 빈 자리라는 뜻이지만, 그만큼 결제가 진짜임을 보여줘야 한다. 이 섹션의 출처는 모두 검색 요약 기반이라 수상 순위는 "보도된 것"으로 다뤄야 한다.

**데이터 시장의 경쟁자들은 대량 판매, 우리는 회차별 동의다.** Ocean은 compute-to-data, Vana는 TEE 검증 DataDAO, Story/Poseidon은 온체인 라이선싱으로 "데이터를 옮기지 않고 판다"를 이미 주장한다 ([Ocean docs](https://docs.oceanprotocol.com/developers/compute-to-data), [Vana](https://vana.org/blog/accelerating-ai-data-revolution), [Blockworks](https://www.blockworks.co/news/poseidon-raises-15m-ais-data-layer)). 이들은 AI 랩에 묶음으로 판다. 반면 AgentRail은 **개인 에이전트가 회차별로 협상하고, 기관 에이전트가 기계로 결제하고, XRPL에서 정산하는** 조합이다. 이 조합을 하는 사례는 찾지 못했다. GA4GH Passport의 `ControlledAccessGrants` visa는 연구자 자격을 기계 판독 형태로 연합해 전달하는 표준이다 ([GA4GH Passport paper](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC8591913/)). 우리 `ETHICS_REVIEW_SLEEP` Credential을 "온체인 visa"로 설명하면 연구 기관 심사위원에게 바로 읽힌다.

**빌더 사후분석이 꼽는 실패 패턴은 AgentRail이 이미 피한 것들이다.** 40건 동시 결제에서 잔액 $10에 $70이 나간 사례가 있다(검사와 지출이 원자적이지 않음) ([DEV](https://dev.to/quinn_854b15f517d8632ed4f/we-fired-40-payments-at-our-own-agent-at-the-same-instant-28-got-through-12-didnt-75m)). 건당 한도만 있고 총액 한도가 없는 사례도 있다 ([Proxy](https://www.useproxy.ai/blog/ai-agent-overspend-postmortem)). 같은 프로세스 안의 한도는 프롬프트 주입으로 우회된다는 지적도 있다 ([Misthos](https://github.com/AZAR2305/Misthos)). 우리 쪽에는 `test_concurrent_orders_...`(SQLite `BEGIN IMMEDIATE`), `mandates.total_drops`·`per_order_limit_drops`, `test_llm_is_never_on_the_decision_path`, 다중서명 treasury가 있다. 각 사례에 하나씩 대응한다. 영상에서 이 대응 관계를 명시적으로 말하는 것만으로 점수가 오른다.

## 넣을 것 / 넣지 말 것

**넣을 것 (총 약 2시간 15분, dashboard polish와 블록 5 일부에서 확보).**

1. **x402 rail 스펙 준수 + Testnet 1회 실행**(60분). `ledger/x402_rail.py`에서 Memos를 빼고 `InvoiceID = sha256(order_key)`로 바꾼다. `engine._release`의 대조 로직도 rail별로 맞춘다. 대가는 DepositAuth 없는 seller에게 1건 순차로 보낸다.
2. **AP2-style mandate 체인**(45분). `mandates`에 `max_amount`·`intent_expiry`를 추가하고, CartMandate 해시와 `mandate_hash`를 memo에 넣는다. 테스트 1개(`test_payment_memo_...` 확장)를 추가하고, 대시보드 "LLM 제안 → 코드 판정 → 원장" 3열의 각 열에 mandate 이름을 붙인다.
3. **KYB(Credential + DepositPreauth)**: PLAN 블록 3을 그대로 진행한다.
4. **A2A Agent Card 정적 서빙 + A2A 모양 로그**(30분). `SendMessage`, `TASK_STATE_INPUT_REQUIRED` 이름을 쓰고 IntentMandate를 `data` part에 담는다.
5. **ISO 27560 / GA4GH 용어 정렬**(문서 위주 20분). README 표 "Standards alignment"에 AP2, ACP, x402, A2A, KYA, GA4GH, ISO 27560을 각 한 줄로 적는다.

**시간이 남으면.** DID 1건(20분), MCP 서버(45~60분). 둘 다 블록 6 통합 Testnet 실행이 녹색이 된 뒤에만 한다.

**넣지 말 것.**

- **Batch**: SDK 업그레이드와 주소 변경 위험이 있고 활성화가 미검증이다.
- **Token Escrow RLUSD/MPT**: 플래그와 faucet이 불확실하다.
- **x402 `upto`·payment channel**: 3일 된 스펙이다.
- **Permissioned Domain**: 강제 지점이 없다.
- **MPT `DomainID`**: `temDISABLED` 가능성이 있다.
- **Web Bot Auth 서명**: HTTP 경계가 없다.
- **실제 Skyfire 연동, `a2a-sdk` 서버 통합**.

이 기술들은 README "Next steps"에 이름만 올린다.

## Conclusion

이번 조사로 바뀐 핵심 인식은 두 가지다. 첫째, x402의 XRPL 바인딩은 memo가 아니라 `InvoiceID` 해시로 주문을 묶는다. 따라서 AgentRail에는 증거를 남기는 방식이 두 rail(memo 기반 Payment, InvoiceID 기반 x402)로 나뉘고, 이 차이를 엔진의 검증 로직이 명시적으로 알아야 한다. 이것을 놓치면 보너스 데모가 프리즈 직전에 깨진다. 둘째, AP2·ACP·x402·KYA가 각각 의도, 상한, 정산, 신원을 맡지만 "상한을 누가 강제하는가"에는 어느 표준도 답하지 않는다. AgentRail의 다중서명 treasury, 원자적 예약, DepositPreauth는 바로 그 빈칸을 원장으로 메운다. 그러니 새 기능을 더 붙이는 것보다 기존 기능에 표준 이름을 정확히 붙이는 쪽이 남은 5시간의 가장 높은 수익률이다.

## 정정과 추가 (설치된 x402-xrpl 0.3.4 코드 직접 확인)

보고서 작성 후 레포가 쓰는 `x402-xrpl==0.3.4` 휠을 열어 확인했다. 위 결론 1번과 2번을 아래처럼 고친다.

**1. memo 문제는 "필수 수정"이 아니다.** T54 SDK의 `XRPLPresignedPaymentPayerOptions.invoice_binding` 기본값은 `"both"`로, `Memos`와 `InvoiceID=sha256(invoiceId)`를 함께 넣는다. T54 facilitator는 자기 SDK 기본값을 받아 주도록 만들어져 있으니 현재 rail(`ledger/x402_rail.py`)은 T54에서 동작할 가능성이 높다. 엔진의 InvoiceID 대조도 blob에서 읽은 값과 비교하므로(`invoice_field_of(tx_blob)`) rail과 무관하게 맞는다. 공식 x402 스펙에 맞추려면 `invoice_binding="invoice_id"` 한 줄이면 되고, T54가 이것도 받는지는 Testnet에서 한 번 확인한다. 병렬 서명은 payer가 `autofill`로 sequence를 채우므로 x402 결제는 1건씩 순차로 보낸다.

**2. AP2식 mandate는 직접 만들 필요가 없다. SDK에 이미 있다.** `x402_xrpl.vi`가 Mastercard Verifiable Intent L1→L2→L3 체인을 구현한다.
- L1: 발급자 credential(SD-JWT). 원래 Trustline 발급자가 서명하지만, 데모에서는 우리 쪽 발급자 키(예: 기관 재무/윤리위원회)로 로컬 서명한다.
- L2 `sign_l2_delegation`: 소유자 키가 에이전트 공개키에 위임하고 `constraints`(예: `per_transaction_max`, `allowed_assets`, `allowed_chains`)와 `exp`를 SD-JWT로 묶는다. AP2 IntentMandate + ACP `allowance.max_amount` 역할.
- L3 `sign_l3_final_action`: 에이전트 키가 주문 1건의 `paymentRequirementsHash`와 `invoiceId`에 서명한다. AP2 Cart/PaymentMandate 역할.
- `build_verifiable_intent_chain`으로 묶어 facilitator에 `extensions.x402Secure`로 보낼 수 있다(호스티드 facilitator가 Trustline 검증을 호출). 이 원격 경로는 Trustline 발급자가 필요해 위험하므로 데모 주 경로에서는 쓰지 않고, 엔진이 결제 직전에 체인 서명과 constraints를 스스로 검증하는 데만 쓴다.

결과적으로 "LLM 제안 → 코드 검증 → 원장 강제"가 표준 어휘로 이렇게 읽힌다: LLM이 주문을 제안 → 엔진이 L2 위임 범위와 L3 서명을 검증(+기존 예산·동의 정책) → XRPL이 다중서명 금고·Escrow·DepositPreauth로 강제. 체인 해시(L3 sha256)를 Payment memo와 x402 `invoiceId`에 넣으면 원장 tx 하나가 위임 증거 하나를 가리킨다.
